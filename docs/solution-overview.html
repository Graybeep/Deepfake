1. Problem Statement Understanding

Synthetic and manipulated media — face swaps, reenactment video, cloned voices — has become cheap to produce and fast to distribute. On social platforms the damage is done in the first hours of circulation, long before any manual verification can catch up. The task is to build a system that helps detect such content.

Reading past the surface statement, four constraints shape everything below:

1.1 The output is a triage signal, not a verdict

No detector is correct all the time, and detection accuracy degrades sharply on media the model was not trained on. A system that returns a confident "FAKE" is more dangerous than useful: a false positive on authentic footage is itself a form of misinformation, and it is the kind that gets someone accused. The honest output is a score with a band and an explicit uncertainty region, routed to different handling — not a binary label.

1.2 The input is hostile

Every uploaded file is attacker-controlled. It is parsed by media decoders with a long history of memory-safety bugs, and the scores themselves can be moved by adversarial perturbation of the input. Both facts have to be designed around rather than assumed away.

1.3 The media is biometric, so retention is a liability

Uploads are faces and voices. Storing them indefinitely creates a growing breach surface and a regulatory exposure that grows with the archive. Deletion must be the default and must be verifiable, while still keeping enough evidence that a disputed result can be re-examined.

1.4 A result nobody can reconstruct is worthless

If a decision is challenged weeks later, "the model said 84" is not defensible unless the exact weights, the aggregation method and its parameters, and the hash of the analysed bytes were all recorded at decision time. That record is a first-class deliverable, not logging.

Explicit non-goal This system does not decide whether content is true, nor whether it should be removed. It detects signals of synthesis and manipulation and routes them for handling. Authenticity and truthfulness are different questions.

2. Proposed Solution

A service that accepts video, image or audio and returns a calibrated manipulation score, a routing band, and a reproducible audit record — with the underlying biometric media deleted on a timer by default.

2.1 Three pipelines, one decision path

Each modality is analysed by a pipeline suited to it, but all three converge on shared aggregation, band routing and retention logic. This keeps one place where a score becomes a decision, rather than three subtly different ones.

2.2 Score the parts, then aggregate deliberately

A model scores individual frames, faces or audio chunks. Those per-item scores are combined with a confidence-weighted trimmed mean — never a plain mean, which a handful of badly aligned faces can drag anywhere. Items are weighted down by detection and alignment confidence, so a frame whose face was barely found counts for less.

2.3 Refuse to guess

When face extraction returns nothing, the result is undetermined. It is never quietly collapsed into "authentic". When more than one face is present, each is scored and the item rolls up to worst-case severity, so a manipulated face in a crowd is not averaged away.

2.4 Bands, not percentages

The aggregated score maps to a band that determines handling. The bands form a total partition of the range, so routing has no undefined input.

ScoreBandHandling
< 20Likely authenticAuto-clear, delete on schedule
20 – 40Leaning authenticAuto-clear, delete on schedule
40 – 60UncertainFlagged for review + alert (normal urgency)
60 – 80Leaning manipulatedFlagged + alert (low urgency); still deletes on schedule
> 80Likely manipulatedFlagged + alert; extended retention window opens
—UndeterminedNo usable signal; flagged, never scored as real or fake

The 60–80 region gets particular care. It sits directly below the high-severity threshold, whose calibration is not trusted enough to display as a raw percentage, so it is logged and flagged rather than passed silently into normal deletion.

3. System Architecture

3.1 Detection pipelines

3.2 Service topology and trust boundary

Network layout is a security control, not organisation. The container that parses attacker-supplied media has no route off the host.

3.3 Request lifecycle

  1. Client requests a job. The gateway rate-limits, creates the Postgres row, and returns a presigned POST grant.
  2. Client uploads bytes directly to object storage — large media never transits the API.
  3. Client notifies the gateway, which enqueues the job. The notify endpoint is idempotent.
  4. CPU worker decodes, samples, extracts and aligns faces (or chunks audio into spectrograms).
  5. GPU worker scores every item and writes per-item rows.
  6. Router aggregates, assigns a band, raises flags, and triggers deletion of the working media.
  7. Status is pushed over WebSocket throughout, with polling as the reconnect fallback.

4. Key Features

4.1 Verifiable deletion by default Tier 1

Raw uploads and derived face crops are TTL-deleted when inference completes. Every delete path — the completion trigger, the crash-recovery sweeper, and cold-storage expiry — checks a hold flag first. The flag column and the check that reads it shipped in the same commit as the delete path, before anything could set it true.

4.2 The job row is the audit trail Tier 1

Every result carries the SHA-256 of the analysed bytes, the model_version_id that produced the scores, and the exact aggregation method and parameters. Per-item scores are retained after the media is deleted — they are numbers, not biometrics — so a disputed result stays examinable without keeping anyone's face.

4.3 Upload path that cannot be used as free storage Tier 1

Uploads bypass the API by design, which means ingress rate limiting never sees those bytes. The grant is therefore a POST policy carrying a signed content-length-range condition, which object storage itself enforces. A presigned PUT would have signed the URL but not the body length — an unbounded write to the bucket.

4.4 Extended retention window Tier 2

A high-band result copies the face crops that drove the score — not the full raw source — into cold storage under a fixed 30-day timer, so a dispute has the specific evidence to re-examine while the original upload is still deleted on schedule.

This is not a legal hold It is a fixed timer that auto-expires, and it is described that way everywhere in the code, the API responses and this document. A timer that quietly expires mid-dispute would be a liability disguised as a safeguard. Relying on it for an actual dispute needs legal sign-off that this codebase does not attempt to assert.

4.5 Isolation instead of AV scanning Tier 3 substitute

The preprocessing worker opens attacker-supplied media with no antivirus in front of it. It runs on an internal-only network with no route off the host, read-only root filesystem, all capabilities dropped, no-new-privileges, a noexec tmpfs, and process and memory caps.

4.6 Resilience and honest failure

  • DLQ — bounded retries, then dead-letter with a log line, rather than silent loss or infinite retry.
  • Durable status — Redis runs with AOF and RDB enabled, and the service refuses to start without it, so a restart cannot vaporise in-flight job state.
  • Crash recovery — a sweeper finds completed jobs still holding bytes and finishes the deletion, subject to the same hold gate.

4.7 Advisories attached to every result

Results carry machine-readable advisories stating that scores are manipulable by adversarial perturbation, and — while the stub backend is active — that the score is a placeholder rather than a detection.

6. Implementation Plan

Hardening is deferred in explicit tiers. The point of naming tiers is that nothing gets skipped silently — a deferred item is written down as deferred, not quietly omitted.

The phases below are the delivery record of the original five-day build. That deadline has since been lifted, so the tiers now describe dependency and order rather than what fits in a week. Some deferrals were justified purely by the clock and are now open; others were gated on something real — trained weights, a held-out calibration set, legal sign-off — and are unchanged by having more time. Available time schedules work; it does not by itself justify building something half-way.

6.3 Stated limitations

What this system does not claim
  • No adversarial robustness. Scores are manipulable by adversarial perturbation of the input. This is documented, not hidden, and every result says so.
  • No legal hold. The extended retention window is a fixed timer that auto-expires.
  • No production-validated calibration. Calibration is a launch snapshot, not tied to a recalibration pipeline.
  • No compliance assertion. Scoped deletion and a partial audit trail are meaningfully better than nothing, but compliance is a legal determination this codebase does not get to make.
  • Not a detector yet. The default backend is a deterministic stub that derives a score from a hash of the input. It exists so the pipeline could be built and proven before weights landed. It carries no detection meaning, and says so in every result it produces.

The last point is the one most worth stating plainly: what has been proven so far is that the system works end to end — ingest, scoring, aggregation, routing, deletion and audit. What has not been proven is detection accuracy, which is a property of weights that are not yet loaded. Conflating the two would be the single most misleading thing this document could do.
